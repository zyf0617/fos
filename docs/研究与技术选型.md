# AegisOS：近期研究与成熟技术选型

检索与核对日期：2026-10-23。实现基础：`2c52073`。架构依据仍为 [AegisOS_ARCHITECTURE.md](../../../AegisOS_ARCHITECTURE.md)。

## 1. 本轮决策

当前适合采用的组合是：进程作为执行实体、组作为资源主体、内核强制服务门禁、事务式页预算、分类失败计数和可过滤的有界事件环。后续先完成进程生命周期与RR，再评估组间公平调度；文件系统就绪后再实现对象权限。

本轮实际增加两项：

1. 借鉴 Linux cgroup 的事件分类思路，将“组预算拒绝”和“通过预算后物理分配失败”分开统计，保存分配阶段原因。
2. 借鉴 Linux Event Tracing 的过滤思路，允许过滤成功syscall事件，保留生命周期、拒绝、故障和分配失败；主动过滤、入环和覆盖分别计数。

这里是机制借鉴与本地实现，不是移植Linux控制器或tracefs，不宣称完成其全部语义。没有引入外部源代码，也没有复现下列论文的性能结果。技术取舍和应用方案均为结合本项目的分析判断。

## 4. 成熟技术：可复用的语义与边界

| 官方来源 | 值得参考的机制 | 本项目的适配判断 |
| --- | --- | --- |
| [Linux cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html) | 进程组聚合、层级约束；memory.events区分不同内存事件 | 当前采用组聚合和事件分类，协作式生命周期扩展的fork已继承组。尚无层级控制器、回收或OOM killer，不能照搬事件名和保证 |
| [Linux PSI](https://docs.kernel.org/accounting/psi.html) | 衡量CPU、内存与I/O资源等待造成的时间损失 | 等待时间需要调度和I/O状态支持；当前页数峰值和拒绝次数不是PSI，暂不实现同名指标 |
| [seccomp BPF](https://docs.kernel.org/userspace-api/seccomp_filter.html) | 缩减syscall攻击面，检查直接参数；官方明确单独过滤不是完整沙箱 | 现有允许集合继续作为入口门禁。未来参数规则避免重复读取不可信指针造成TOCTOU；不引入BPF解释器来管理仅8个服务 |
| [Landlock](https://docs.kernel.org/userspace-api/landlock.html) | 可叠加的权限约束与对象操作规则 | 继续采用只能收紧的约束方向；对象/路径规则要等文件系统，当前mask不是Landlock规则集 |
| [FreeBSD Capsicum](https://man.freebsd.org/cgi/man.cgi?query=cap_enter&sektion=2) | capability mode限制全局命名空间访问，继承已持有的资源 | 文件系统阶段参考“内核资源句柄+对象权利”，避免仅凭路径字符串判断权限；当前syscall mask不等于对象能力 |
| [Linux EEVDF](https://docs.kernel.org/scheduler/sched-eevdf.html) | 依据公平份额欠账及虚拟截止时间选择任务 | 先保留RR基线，组间加权选择、组内RR作为实验候选；延迟目标和休眠公平性明确后再评估EEVDF复杂度 |
| [sched_ext](https://docs.kernel.org/scheduler/sched-ext.html) | 可替换调度策略，检测错误/停滞后回退基础调度 | 借鉴可切换和回退的实验组织；当前没有Linux BPF/sched_ext依赖，不做接口兼容承诺 |
| [Linux Event Tracing](https://docs.kernel.org/trace/events.html#event-filtering) | 内核中按事件字段过滤，减少无关输出 | 本轮采用固定、可解释的成功事件过滤，无运行时表达式引擎；同时记录过滤数和覆盖数 |
| [Wasmtime/WASI安全模型](https://docs.wasmtime.dev/security.html#filesystem-access) | 显式导入能力，文件访问以获授资源为边界 | 可作后续用户态工具运行时的候选；当前缺少宿主服务和完整用户环境，不优先集成Wasm引擎 |
| [gVisor](https://gvisor.dev/docs/architecture_guide/intro/)、[Firecracker](https://github.com/firecracker-microvm/firecracker/blob/main/docs/design.md) | 用户态应用内核或microVM提供额外宿主隔离边界 | 适合后续真实Agent在Linux宿主上的外部对照；与当前自研内核的职责不同，不作为可直接嵌入的组件 |

cgroup的 `memory.high` 包含限速/回收行为，`memory.max` 与其OOM机制关联；本内核只有分配与拒绝，没有这些前提。因此先选事件分类与事务预算，不伪造“软限额”或“内存压力”控制器。

## 5. 当前已经应用的具体变化

### 5.1 分开统计预算与分配失败

入口为 `mem/uvm.c:allocate_range`。`agent_charge` 拒绝只增加 `quota_denied`。通过预算后，如果临时根页表、用户数据页或中间页表分配失败，先完成原有页和预算回滚，再调用 `agent_allocation_failed`：

- 组的 `allocation_failed` 每失败事务增加1；成功不增加。
- kind=7记录失败阶段，detail=1临时根、2用户数据、3中间表。
- 事件中的pages是回滚后的组预算占用，失败前的预留峰值保留。
- 非当前/未入组页表不计入组；无效地址、节点池不足或权限拒绝不冒充这种物理分配失败。

命名和统计属于本项目，没有复制Linux `memory.events:oom` 的语义。测试逐分配点核对计数、阶段与PTE/页池/预算恢复。

### 5.2 过滤成功事件，保留失败线索

`AEGIS_AUDIT_SUCCESS=0` 在取组快照和写环之前过滤成功syscall完成事件。其他事件仍记录；未知服务或参数失败的syscall完成状态为-1，也会保留。

`agent_audit_snapshot` 返回累计入环数、主动过滤数、环覆盖数；主动过滤不消耗序号，游标的lost仍只反映入环后被覆盖的记录。关闭全部审计时这三个值均为0。

过滤计数用独立原子更新，入环计数用审计锁；返回的是观测快照，不是所有并发事件的同一事务切面。成功调用洪泛不会挤掉既有拒绝，但失败事件洪泛仍会覆盖固定环，不能宣称永久安全日志。

## 6. 采用顺序与验证门槛

| 顺序 | 决策 | 依赖与验收 |
| --- | --- | --- |
| 现在 | 分类事件和可选过滤 | 故障注入能区分预算/分配原因；过滤不关闭保护；成功洪泛保留拒绝；三种审计配置均通过 |
| P1 | 进程生命周期与组继承 | RR、fork/wait/exit；成员名额、复制、收费作为同一事务，逐失败点回滚 |
| P1 | 组级公平性候选 | 组间加权选择、组内RR；A组4进程/B组1进程，测CPU份额、吞吐、响应、饥饿；工作量相同且考虑休眠/唤醒 |
| P1 | 对象权利与受信控制面 | 文件描述符/exec存在后才能委托、收紧和继承权利；不可信程序不能写策略或自选更高预算 |

| 暂缓 | EEVDF全量实现、BPF动态策略、WASM引擎、共享运行时/COW分支、microVM迁移 | 当前依赖不齐；先保存参考与实验问题，不扩大交付承诺 |

## 7. 本轮对照实验如何解释

当前微基准增加第四种模式 `filtered`，与baseline、enforce、audit使用完全相同的用户二进制。保存于 [选型应用后的对照](benchmarks/agent/2026-10-23-selected/README.md)：每模式3次独立启动，每次每种工作负载31批，共12次启动、744批。

测量仍为QEMU guest time的批均值；成功查询和成功映射往返对过滤方案较有利。拒绝风暴、真实Agent吞吐和实板尚未计时，不能用此结果概括所有工作负载或把开销下降写成任务能力提升。

本轮结果还出现配置排序不单调：map-cycle的audit中位数略低于enforce，filtered低于enforce。应考虑编译布局、缓存、宿主和TCG影响，不能把这种排序当作机制固有优势。选择过滤首先依据记录量和拒绝保留测试，保留全部测量数据供后续复核。

原 [三模式数据](benchmarks/agent/2026-10-23/README.md)保留为 `2c52073` 对应阶段的历史证据，源码摘要与本轮不同。性能比较应使用同一轮内的模式，不跨轮混算百分比。

### 后续落地：进程资源与组继承准备（2026-10-23）

依据前文“复用进程生命周期、按组聚合资源”的选型，已实现 `proc_clone_resources`：先原子预留组成员和全部用户页，再复制独立地址空间、trapframe与区间节点；失败整体回滚。共享组对象使收紧策略能同时作用于目标，避免复制出独立且可放大的预算。该接口本身不发布子进程；随后可选生命周期扩展已在其上接入真实fork/exit/wait与协作运行，验收见[生命周期记录](PROCESS_VALIDATION.md)。这不作为抢占公平性或真实Agent收益的证据。实施顺序见 [后续开发计划](后续开发计划.md)。
