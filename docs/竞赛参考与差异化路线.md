# 竞赛参考与 AegisOS 差异化路线

调研：2026-10-23。按用户所说的“去年”研究 2025 年作品；当前具体参赛依据仍是 2026 华东区域赛材料。全国赛与区域赛的任务范围分别核对，不能因为技术内容有重合就认为评分和交付要求完全相同。

## 1. 已确定的方向

[AegisOS_ARCHITECTURE.md](../../../AegisOS_ARCHITECTURE.md) 是架构依据。四个支柱为 Agent Group、Capability & Resource Isolation、Agent-aware Scheduling、Observability / Audit / Trace。本轮在 Lab 5 上落实组归属、共享用户页预算、服务权限和有界审计；调度与文件/工具约束依赖后续课程模块。

组级计数、权限和环形日志是已有的系统设计工具。AegisOS 的候选贡献应落在：这些机制如何在自己的内核中形成一致、可验证的资源生命周期，以及对具体 Agent 工作负载是否产生可测收益。目前只完成保护原型，尚未证明学术新颖性或竞赛领先性。

先以组织方的 [2025 内核获奖作品汇总](https://github.com/oscomp/os-competition-info/blob/main/os-kernel-winners.md) 核验：NoAxiom 在一等奖名单中。该列表还包含 Del0n1x、Chronix、rustflyer、StarryX、Starry Mix、undefined、火箭队等；列名不代表本轮已阅读其源码。

本轮实际阅读上述三个公开项目的 README/设计概述、目录与材料组织。Starry Mix 的赛事 GitLab 链接重定向登录页；NoAxiom final.pdf 的网页未成功返回正文，因此不声称已通读该 PDF。未复制这些项目代码，也未复现实测它们的性能。

| 案例 | 从公开资料读到的做法 | 转化为 AegisOS 的行动 |

## 4. 现在形成的展示主线

提出问题：一个工作负载可以通过堆、栈、mmap 多条路径消耗内存；单个服务的参数检查不足以形成共享资源预算。

机制：将用户进程关联到组，在三个增长路径的共同事务分配入口预留预算，拒绝服务和超限请求，失败返还预算，正常释放和退出均归还收费；审计记录原因和资源快照。

证据：真实 ecall 拒绝、未修改被保护缓冲区、满额后拒绝、释放后复用、逐分配失败点回滚、组与物理资源回收、开关关闭时课程回归。当前未运行真实多进程 Agent，因此先把这些称为可复验的保护原型。

后续闭环：多进程/fork 继承 → 进程数预算接入 → 两级调度及公平性对照 → 文件/工具约束 → 用户态管理与演示。调度研究必须先有可运行的 RR 基线和真实多个进程。
